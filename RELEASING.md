# Releasing ScriptForge

The first public version is **1.0.0**, tag **v1.0.0**, title **ScriptForge v1.0.0**. Development builds do not consume public versions. Nothing publishes on push. The **Official release** workflow requires deliberate dispatch from reviewed main.

## First-release prerequisites

1. Review the source inventory, exclusions and security audit. Obtain explicit approval before pushing to wdk08/ScriptForge. Do not create another repository or force-push.
2. Review GPLv3 compliance in docs/LICENSING-REVIEW.md. ScriptForge original work is GPL-3.0-only; preserve all third-party terms. Verify source-built Piper provenance, retained notices, source packaging and the matching source-release asset before uploading any binary.
3. Configure the production public verification key and private signing secrets below. Never use the public throwaway test vector as a production key.
4. Use the owner-selected distribution policy: ad hoc Mac signing, no notarization, unsigned Windows publisher identity. Only Tauri updater signing secrets are required. Include INSTALLING.md warnings; do not weaken updater verification.
5. Review [release readiness](docs/RELEASE-READINESS.md). Intel/Windows builds and a real installed-version update on both platforms remain acceptance steps.

## Updater key — already generated by the owner

Do not generate a new key for every release. The owner's production pair is outside the repository. Only its public key belongs in source.

For a new setup needing its first pair, from this project:

```sh
mkdir -p ~/.config/scriptforge-signing
npm run tauri -- signer generate -w ~/.config/scriptforge-signing/updater.key
```

Choose a strong password interactively. Never pass it as a command-line argument or paste it into chat. Do not overwrite an existing key with --force.

- updater.key is the encrypted PRIVATE key. Never commit, print, package, or upload it as a release artifact.
- updater.key.pub is PUBLIC. Configure it with:

```sh
node scripts/set-updater-key.mjs ~/.config/scriptforge-signing/updater.key.pub
```

The helper accepts only a public .pub file, validates its Tauri/minisign format, and writes the public value to tauri.conf.json. It never reads the neighboring private key. Keep an encrypted offline private-key backup and store its password separately in a password manager.

## GitHub Actions secrets

Repository security-setting changes require the owner's explicit approval. Use this repository → Settings → Secrets and variables → Actions → New repository secret. Never place credentials in source, public variables, workflow text, build logs or chat.

| Secret | Value |

| TAURI_SIGNING_PRIVATE_KEY | Contents of the encrypted updater.key file |

From your own trusted terminal, GitHub CLI can upload the file without printing it:

```sh
gh secret set TAURI_SIGNING_PRIVATE_KEY --repo wdk08/ScriptForge < ~/.config/scriptforge-signing/updater.key
```

## Validate builds without creating a release

After explicit push and validation-run approval, dispatch **Validate desktop
builds** on the exact reviewed main commit. This read-only-repository workflow
runs source/license checks and tests, makes corresponding source available with
its validation artifacts, builds on native Apple Silicon/Intel/Windows runners,
verifies updater signatures/platform policy, runs isolated packaged save/reopen
checks, and retains installer/checksum/source artifacts for 14 days. It does not
create a GitHub Release, tag or source push. These Actions artifacts are test
builds, not a public release. Download the matching source artifact with binaries.

Manual quarantined-download/OS policy checks and a real installed-version update
remain separate acceptance tests. See docs/PLATFORM-VALIDATION.md. Source upload,
workflow execution, releases and publication still need the owner's authorization.

## Prepare changes and a release commit

1. Finish changes in Codex and run the existing editor/storage tests.
2. Choose semantic versioning: 1.0.1 fixes, 1.1.0 features, 2.0.0 incompatible changes. Do not increment for each preview build.
3. Synchronize package.json, both root version entries in package-lock.json, tauri.conf.json, Cargo.toml and the scriptforge entry in Cargo.lock. About reads the actual running package version; no UI version string needs editing.
4. Add releases/vX.Y.Z.md with accurate changes/limitations. The workflow uses it as the release body and official Tauri tooling generates updater metadata/notes.
5. Run:

```sh
npm ci
npm test
npm run check
npm run desktop:test
npm run release:check -- --production
npm run audit:public
npm run audit:history
npm run licenses:check
npm run release:source
npm run test:browser -- --workers=2
npx playwright test --config=playwright.webkit.config.js --workers=2
npm run desktop:build
```

Optional real-model tests need SCRIPTFORGE_PIPER_MODEL and SCRIPTFORGE_PIPER_CONFIG pointing to a licensed compatible local voice. There is no separate TypeScript/lint pipeline; check validates JS syntax and Cargo validates Rust. desktop:build uses the local ad hoc/no-updater-artifact override; desktop:release requires the production signing environment. Prefer the controlled workflow for production builds.

6. Inspect the audit and staged files. User data, private credentials, .env, local grants, historical validation screenshots/PDFs, dependencies and build outputs are excluded. Synthetic test fixtures and upstream notices remain included.
7. Prepare a normal main commit with the author's preferred identity. Obtain explicit approval before git push origin main. Do not reset history, overwrite tags or force-push.

## Dispatch the workflow

1. GitHub → Actions → Official release → Run workflow; select main.
2. Enter the synchronized version (first: 1.0.0) and complete reviewed 40-character main HEAD commit SHA. The workflow rejects another commit/branch/repository.
3. Confirm licensing review only after it is resolved.
4. Leave Publish off for a nonpublic draft. Creating/uploading this draft still requires owner approval. A draft is not stable discovery and does not prove end-to-end updating.
5. To publish, obtain explicit approval, enable Publish, and enter ScriptForge vX.Y.Z exactly. This authorizes that specific run, not future releases.

The workflow checks draft attachment and temporary-tag permissions before expensive validation. The reusable validation workflow builds and signs once on Apple Silicon macOS, Intel macOS (macos-15-intel), and Windows x64, verifies signatures, and exercises real installed updates from the v1.0.1 source tag with isolated diagnostic endpoints. The candidate update bytes are unmodified production artifacts. Only after all platforms pass are those same-run artifacts attached to the exact-commit draft, with the verified corresponding-source archive attached first. No second installer build occurs. Uploaded SHA-256 digests must match the validated artifacts; latest.json binds all three platforms to their actual uploaded asset IDs. Publication creates an explicit exact-commit tag and publishes by numeric release ID, avoiding implicit tag creation during a release edit. Only release-writing jobs receive contents:write; validation is read-only.

Expected files: ScriptForge-X.Y.Z-source.tar.gz and its SHA-256 file, two DMGs, two .app.tar.gz updater archives with signatures, Windows NSIS setup.exe and signature, latest.json, and per-platform artifact .sha256 files. Required metadata targets: darwin-aarch64, darwin-x86_64, windows-x86_64. Official installer-specific aliases are allowed. Metadata references actual uploaded assets and version-bound signatures over HTTPS. The native plugin cryptographically verifies packages; structure checking alone is not signature verification.

An existing release/tag is refused instead of overwritten. Inspect failed drafts and rerun failed jobs only when safe. Do not delete/reuse release assets blindly; cleanup or destructive changes require separate approval.

## Verify publication and real updates

Check GitHub Releases and the workflow summary. After publishing, the workflow tests the public latest/download/latest.json endpoint and public binary downloads. A failure at this stage happens AFTER publication and needs investigation; the workflow does not silently delete/unpublish the release.

Validate separately on a Mac and Windows machine:

1. Manually install the reviewed first updater-enabled build; About must show its installed version.
2. Create synthetic screenplay content, settings, margins, voice assignments and a backup; leave pending edits.
3. Use a later approved version to test background discovery once per launch, manual checking, actual notes, progress and Later.
4. Test offline, download, metadata, missing-signature and invalid-signature failures. Never disable TLS/signature checking to pass a test.
5. On Windows, confirm the save barrier before installer-driven exit. On macOS, use Restart Later, make another edit, then Restart Now and verify the second save barrier.
6. Reopen and compare the exact script, linked file, preferences, recovery, voices and backups; check the new About version and manual up-to-date result.

Do not claim end-to-end success until a real installed version has updated and reopened with its data intact. Mock UI checks and real native signature/download tests do not establish installer success.

Do not publish a fake production version solely to test. Propose an approved prerelease using a separate test identity, key, endpoint/configuration and isolated synthetic app data. Keep experimental metadata away from production users. The stable workflow intentionally has no experimental-channel switch; a test channel requires its own review and approval.

## Data preservation and development transition

Keep com.scriptforge.desktop unchanged. Screenplays are outside the application bundle; native grants/backups use OS app-data; recovery, settings and voices use WebView storage. Installers replace application assets, not these data locations. Do not uninstall with an option that removes application data.

Development 0.1.9 is below 1.0.0 but has no updater, so manually install the first official build. Any hypothetical testing version above 1.0.0 also needs manual replacement. Default comparison permits newer versions only; no downgrade comparator is enabled.

## Failures, keys and rollback

- Missing metadata/404 before the first approved release is expected. Automatic checks stay quiet; manual checks report failure. Inspect URLs/assets rather than clearing data.
- Signature failures: verify that the embedded public key and workflow private key match, the CLI signed the advertised version, and artifacts are unchanged. Never invent signatures or disable checks.
- Save/recovery/preference failures block install/restart and keep editing available. Resolve file permissions/conflicts/storage errors and retry. Updating does not prune or migrate backups.
- Platform checks require an intact ad hoc Mac signature and unsigned Windows status under the selected policy. Publisher identity/notarization are not provided. An OS policy block is not fixed by disabling updater signature checks; follow INSTALLING.md and retain user data.
- Lost private key: restore the encrypted backup/password. Without them, existing users cannot authenticate a new-key update. A manual installation from a separately authenticated trusted download is necessary, retaining app data. This distribution has no certified publisher identity, so a replacement key cannot establish trust by itself. Do not add an unsigned bypass.
- Key rotation needs a reviewed trust transition. Do not casually replace the public key. Keep credentials in approved Actions secrets with restricted human access.
- Faulty release: use an approved release-management action to pause distribution if needed, then publish a HIGHER patch version with the fix/revert. Existing users on the higher bad version will not downgrade automatically. Do not overwrite old archives, pair old binaries with a fake newer manifest, or force-reset Git. Signed-version checks reject mismatched artifacts/metadata.
